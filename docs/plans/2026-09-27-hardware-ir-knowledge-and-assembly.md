# 硬件执行 IR、分层知识与 Chief 选择装配模板

## 用户要求（2026-09-27）

- 执行 IR 的硬件词汇与约束由 Chief 在设备准备阶段通过搜索、设备实验建立，不在插件中预设一套硬件活动原语。
- kernels、ir、reports、versions 按 `<op>/<dtype>` 保存，集成不得混用其他目标的 kernel。
- Chief 从用户提供的材料或仓库示例中寻找、选择装配模板；插件负责占位符替换、已测 shape 的性能选择、分桶表与路由函数。
- 知识层级为 `knowledge/`（HW）、`knowledge/<op>/`、`knowledge/<op>/<dtype>/`、`knowledge/<op>/<dtype>/<shape>/`（明确尺寸区间）。

## 实施边界

只改 Meteor 源仓库和本地测试夹具。现有 C 实验及其冻结快照、证据、API/模型/SSH配置保持原样；不重启或向活动研究注入修改。新增行为用临时 workspace 验证，真实新 Desktop/设备复验单独记录。

## 设计

1. 增加 Chief 的硬件准备 skill 和设备诊断/执行模型接口。诊断请求使用既有 SSH FIFO、持久请求身份、命令限时及释放证据；它们是设备准备证据，不能替代研究作者的 kernel full。执行模型绑定硬件和环境，资源、活动及约束来自文档和诊断证据，区分已测、文档规定与未知。发布不可变模型后，研究的设计快照绑定该模型。通用计算图原语与图结构检查保留；执行活动名称与资源从当前模型读取。
2. 装配模板为 target 的显式选择，保存来源与 hash。研究冻结所用选择。程序提供插槽、bucket 数据及路由生成；无模板的真实 target 返回准备未完成。示例只供 Chief 选择和适配，不作为隐藏默认。
3. 知识条目新增 `scope_level`。shape 层使用 `{shape_id, dimensions:{axis:{min,max}}}`，含端点且保留作者声明的范围。旧 `applicability=hardware` 映射 HW，其余旧条目映射 dtype；不改旧提交内容。物理 JSON 保存来源、证据、范围和内容 hash；共享 SQLite 继续作为索引。默认复用遵循 HW→同 op→同 dtype→匹配区间，显式外域引用标作启发。
4. 保留现有 target 身份、作者绑定、原会话、full 与 comparison 门槛、mock 隔离、预算及集成终态恢复。对两个 op/dtype 使用相同本地标识的场景增加隔离验证。

## 验证

- 动态硬件活动/资源接受与拒绝；缺失或变化模型不能复用旧预期；诊断持久身份、超时/释放及同 FIFO。
- Chief 自选模板、变更冻结、不跨 op/dtype、只选择 PASS 且推荐的测点。
- 四层知识目录、层级继承、shape 边界、旧库升级和重复提交幂等。
- 定向测试后执行语法、类型、构建与必要整体验证。测试报告明确本地模拟与真实设备的区别。
