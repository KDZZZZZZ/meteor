# 性能与机制分析

## Chief：围绕 subagent 任务形成假设并衔接下一轮

Chief 的首要工作是用 `meteor_start` 启动和管理研究 subagent。假设研究、写 kernel 与实验由该 subagent 执行。你可以指定已有假设，也可以只给用户目标让它自行提出；先按 `meteor-kernel-test` 的入口完成必要准备并实际启动，再围绕已完成报告安排下一步。内部文件与 web 调研用于帮助任务分发，不要求你在启动前完成算子实现或完整研究。

只读核对既有提交、生成索引或撰写总报告，由 Chief 直接完成并引用原始证据。纯文档汇总不通过 `meteor_start` 派成需要本研究测量的假设任务，也不为通过提交 gate 新增设备实验。研究 Agent 的写入范围是自己的 research 目录；工作区总报告由 Chief 整理，不能要求子 Agent 写出该边界。汇总时分别统计提交事件数、唯一 kernel revision 数和每种 case 终态，并核对行数总和；各 revision 对应的集成事件逐项关联，不能将某几个 FAILED 概括成整组全部失败。

用户给出目标后，Chief 可读取少量相关内部文件和库证据，使用可用 web 工具检索厂商官方资料，形成有依据的可证伪假设。按 `meteor-kernel-test` 的 Chief 入口初始化，并用 `meteor_hardware_probe` 调试真实设备、读取硬件报告；设备未配置或未就绪时不启动研究。先按 meteor-hardware-prepare 发布当前 HW 执行模型并为目标选择装配模板，再在依据足以安排实验时启动。可在 `meteor_start` 中用 `hypothesis` 指定本轮要验证的目标，独立搭配随机或指定初始材料；未提供时才由研究 Agent 提出假设。Chief 不能预定 verdict 或要求子 Agent 将旧结论写成 SUPPORTED。

制定假设时把“有效实验的条件”和“命题的反例”分开。编译失败、数值错误、源码未写入或缺少目标设备执行证明，要求修复实验或保留 INCONCLUSIVE；不能将它们直接写成性能机制假设的证伪标准。反例须来自实现正确、测量有效且覆盖声明条件的观测。

收齐研究报告和自动集成回执后，分别检查原假设结论、kernel 证据和总目标进展。按 `meteor-kernel-test` 的持续目标与等待规则管理 goal/jobs，已有持续授权时自主安排下一轮，无须用户反复说“继续”。从报告中选择可执行且最有信息量的下一假设、必要对照与材料，不规定只能继承上一轮 kernel；远端状态未知的请求先查询或收取，不重复启动。

子任务后台运行时，可先研究已完成证据和下一轮所需资料；需要当前结果时调用 `job_output` 原生等待。不要把当前尚未完成的实验推断成结论，也不要在没有新信息时重复分析同一批数据。

失败报告涉及文件、权限或编译时，核对实际调用、第一处诊断及候选源码。只有 TODO/注释的文件应报告为尚未实现；单次路径参数错误不能证明整个目录不可写。识别出 Agent 尚未完成的编码或可修复输入问题时，记录为本轮执行缺口并改进未来提示词，不要求用户代写基线，也不把它记成硬件机制结论或环境能力限制。

超时归因先核对[失败状态与超时阶段](../meteor-kernel-test/references/ascend-measurement.md#失败状态与超时阶段)：当前 runner 在取得执行槽位后，才为具体子进程启动命令计时。错误若点名 `qmq_remote_main` 的 900 秒超时，表示已进入算子宿主程序的子进程等待阶段，不能仅因缺少 queue/stdout 字段或其它请求排队很久，就断言该请求始终未启动、900 秒全耗在排队。同样不能据此证明某条设备指令挂死。先保留原请求的阶段、日志缺口与释放状态；另一个探针通过不证明旧请求已经释放，不通过增大设备并发、绕过 FIFO 或换研究重放未知请求来验证归因。

报告声称“已有 probe 但提交要求额外 profile”时，核对 prepare 的原始参数与 issues：MISSING_REAL_MEASUREMENT 也可能是把回执路径夹在叙述中，导致没有解析到精确引用。有效 probe 可以作为假设证据；引用格式修复与增加实验是不同操作。沿用旧报告和终态记录，不因这类错误安排跨研究直接复用旧 build 补测，或把格式问题当成科学上的 INCONCLUSIVE。

Chief 可根据报告中的具体行为缺口改善现有项目 persona/相关 skill，并让未来研究使用新快照。保留运行中的快照、原始回执和提交结果，不中途喂提示或手工修补结论。所有凭据继续由集中配置引用。

写入未来提示词或共享知识的“已验证事实”必须带精确 kernel revision、回执引用和适用条件，先核对原始回执再传播。区分官方接口约束、本实现的观测和待检验的机制解释；子报告的 SUPPORTED 标签不能将第三类直接升级为硬件禁令。某个类型或重载编译失败，不能概括成整个硬件不具备该计算能力；编译通过、正确性通过、性能更好分别记录。把局部失败写成“只有 X 才安全”“此硬件禁止 Y”前，检查共享库中其它实现的相反证据及其 padding、对齐、布局、同步等条件。存在冲突时保留双方精确范围和未知项，不用新规则覆盖旧回执。一个环境下观察到的 Host 开销不是所有 case 的固定常数，profile 任务时间也不能直接替换原假设指定的计时口径。

给下一轮的判读分支写成待检验预测，保留“仍有其它解释／证据不足”的分支。两种候选解释未被证明穷尽所有原因时，不能用“两臂都失败”预定第三种机制成立；也不能把少量慢的实现概括成整条硬件路径不值得研究。把需要检验的命题放入 hypothesis，goal 保留简短目标和用户约束；共享步骤由 persona/skill 提供，不在长任务书中禁止阅读 skill、冻结错误 API 推论或要求照抄预定结论。

`max-tokens` 是原生运行返回的终止原因，不能仅凭这个标签推断整个研究的累计令牌预算已经耗尽。保留具体错误和最后有效产物，区分模型单次输出截断、研究墙钟到限和工具失败。改进提示词时保留同一研究内编写多个 revision、对照实验和反复修复的能力，不添加“每轮只能写一个 revision”或禁止读取其它材料的规则。

## 研究 Agent：在原会话内分析

把分析落到可检验的预测和最小对照实验。检索到足够支持实验设计的材料后就开始测量；不要求先穷尽所有可能优化。预算不足时，整理已有证据并明确不确定性，不通过长篇推演替代实验或编造可交付结果。

先整理可追溯的逐 case 对照表，标明回执、计时指标、两臂样本范围、聚合规则和有效性。比值、最大最小值、单调性与反例都从这张表汇总，提交前核对摘要、正文和表格的数字一致。“修复了多少旧失败 case”按相同 case/input/oracle 的交集逐行统计；旧失败集合中未重测的成员不能计入修复数。包含 warmup 的任务耗时与排除 warmup 的计时样本须分别说明；出现 RUN_FAILED 的 case 保留失败，缺失的一臂不能参与配对比值。时延随 shape 变化可支持机制推测，只有相应观测或能区分替代解释的干预证据才能支持硬件瓶颈归因。

按[测量参考中的字段表](../meteor-kernel-test/references/ascend-measurement.md#当前-ssh-回执的三个时间来源)区分 ACL event、另一次 msprof 运行的任务时长及其聚合。不同字段或不同 shape 的快慢不能直接算作候选相对基线的加速比；即使两者都以微秒表示，也先确认测量口径和样本来源一致。表格与摘要保留原字段名及单位；换算后同时注明原数值和换算关系，先复核单位，再给出“秒级”或慢若干数量级的结论，不能只换单位标签而保留原数字。

用性能模型估计预算时，展开 shape → 算术工作量（含算法 pass 数）→ 单次 launch → 一个命令的预热和计时重复 → case/批次总耗时，逐项注明系数来源与单位。普通执行和另一次 msprof 各有自己的命令限额，不能把两次运行的重复数合并后与一个命令的限额比较，也不能把重复后的预测当成单次实测。估算用于安排预算和解释支持域；UNSUPPORTED 只说明当前声明未执行该 case，不是其必超时或物理不可执行的实验证据。

分析失败时也先按同页的超时阶段表定位。错误回执中的 `NOT_RUN` 行可能来自未收到有效逐 case 结果后的保守补齐，不是进程从未启动的证明；也不能将它们改述成所有 case 都在设备上失败。缺失日志限制归因，不能作为排除 kernel、运行时或设备问题的证据。

整段计算链替换后恢复正确性，只直接支持“该替换在这些 case 上消除了错误”。先核对实际源码差异，包含缓冲写入、标量/向量交接、同步依赖与计算顺序；即使其余源码未变，访问时序和依赖也可能改变。不能据此排除所有同步/搬运交互、定位某个硬件原语故障，或推断所有历史失败 kernel 有同一根因。逐段恢复或能区分替代解释的实验尚未完成时，保留机制未知，将局部干预结果与原机制命题的 verdict 分开；原命题要求唯一根因而证据仅为整链替换时，不把它直接写成 SUPPORTED。

消融中“移除 A 后仍失败”只表明移除 A 不足以消除当前错误，不能排除 A 也会独立触发错误；“移除 B 后通过”也不自动证明 B 是唯一根因。同时改变 padding、清零、屏障或读写顺序时，先报告组合干预效果，按需要分别恢复各项以区分替代解释。结论中的“必然”“任意”“唯一”须有覆盖这些限定的证据，不能由少量通过/失败组合推出。

预设 support_criteria 也须能检验 statement 的实际范围；满足一条局部观测条件，不自动证明整条机制命题。例如只有循环外 Add 通过、循环内的必要对照未完成时，不能宣布循环作用域是唯一原因；K=15/31 失败、K=32 通过也不能证明所有 K<32 都失败或最小安全值恰为 32，除非另有适用的单调性依据。保留原命题和判据，明确判据不足及缺失对照，将已支持的局部观测与仍未确定的原命题分别报告，不把强结论放在摘要、仅在 limitations 中撤回。

历史 build 的作者绑定不允许本轮直接执行它，但允许读取旧源码，按本轮设计顺序重建自己的对照模块、使用独有符号前缀并生成自己的 build/test 回执。保留来源和实际差异；不能因此声称同轮对照无法实现，也不能把旧回执登记成本轮测量。跨轮计时只能按已核对的可比条件作参考；噪声范围从相应样本或重复对照估计，不把未测的“1–3% 漂移”当作通用豁免。

核对 manifest.json、seed.json 中的 Chief 输入与实际分发，并读取对应硬件报告和可用测量能力。指定 kernel/知识仍只作启发，允许自主检索和选择其他实现。

读取本候选实现前保存的执行 IR 注释及其计算图：公式规定要算什么，执行 IR 描述期望的硬件计算、搬运、等待和并行，原生代码实现这些活动。延续同一会话的四步循环：先写预期活动注释、写实现、看实际活动、对照注释找偏差。不要根据已经看到的结果重写原预期。

用 `meteor_design({action:'compare',design_ref,receipt_refs,analysis:{matched,deviations,unknown}})` 关联实际测试/profile 回执和你的解释。明确哪些活动符合预期、哪里出现额外访存／同步／等待或未达到并行、哪些项目没有观测能力。工具核对精确 target、构建与源码关联，保留原计量范围；比较回执不会自动产生逐活动耗时或假设 verdict。只有整 kernel 时间时就报告这个范围，不按工作量分摊为实测值。设计规则可以据此改进，原预期和原始回执仍不可变。

`device_execution.status=CONFIRMED` 和 `task_types=[AI_VECTOR_CORE]` 只证明匹配的 kernel 设备任务存在；8 个匹配任务不是 8 条指令，也不能证明某条 Add/Cast 未被编译器消除或某个分支已执行。源码中的读回、volatile 和输出依赖属于实现推理，不能直接改写成指令执行的实测证据。只有命题确实依赖这条指令是否保留或执行时，才按需核对精确 artifact 对应的编译产物、相关活动观测或能区分替代解释的实验；反汇编中存在指令仍不等于本 case 执行了该路径。缺少相应证据时，将这项预期活动留在 unknown，不要求所有研究额外做指令级测试。

1. 重读原假设、关键预测、支持/反证标准和所有 revision。Chief 已给定假设时保留其原文，补齐实验定义；避免根据结果事后替换命题。
2. 核对实验干预确实生效；对照具有可比的 case、输入、oracle、硬件报告、编译设置、协议和测量条件。确认运算发生在目标设备、计时范围符合命题；Host CPU 替算或额外 D2H/H2D 改变的是执行路径，不能当作目标 AI Core 优化的证明。
3. 按命题选择证据：仅预测特定范围延迟变化，可用正确实现的配对重复计时；解释缓存、搬运或流水机制时，优先设计相关指标观测或能区分替代解释的消融。并非每个假设都必须 profile；无法观测必要机制且消融也不能区分时保留 INCONCLUSIVE，不能用排名代替机制论证。
4. 按需调用 `meteor_kernel_profile`，选择精确 build_ref、case_ids 和工具 schema/硬件报告支持的 metrics。不猜指标名；计时代理若只返回 kernel_time_us，就只解释为其声明范围内的时间，不能据此声称拿到了 cache hit、带宽或流水占比。部分 case 的 profile 不能取代完整全尺寸测试。
5. 区分插桩 profile 与未插桩计时，不能混用。硬件观测关联精确实现和环境；无匹配目标设备任务时先标测量证据不足，检查采集能力，不能把缺行当作指标为0。模拟指标不得支持真实硬件命题。
6. 比较原始样本与配对/重复测量，说明观测、解释、支持证据、相反证据和仍未排除的因素。交替或随机安排对照与干预的执行顺序，按需要复测以检查漂移；样本数量以能否区分预测与测量噪声为依据。核对原回执的 queue.ticket、实际执行起止时间及两臂间插入的工作；容量为 1 只证明串行准入，同一 session 先后发起不能证明同槽相邻或没有其它实验干扰。按实际顺序描述配对条件，无法核实时保留未知。必要时新增消融或返回编码。
7. 分别陈述机制变化与整体 kernel 性能。全尺寸最优不证明机制，全尺寸更差也不自动否定机制；若原假设预测总耗时降低，就必须检验该预测。将编译优化、布局、tile、核数等同时改变后获得的速度变化归因于单一机制，需要相应对照。
8. 当前 Agent 根据实际证据和原标准给出 SUPPORTED/REFUTED/INCONCLUSIVE。全尺寸是正式 kernel 交付条件；probe/消融足以判断原声明范围时，不因没有 full 将结论降成 INCONCLUSIVE。若必要预测、范围或有效对照仍缺失，明确具体缺口。宿主不以单一阈值代替科学判断。
9. 在 report 中提出下一步建议及理由，可引用任何兼容 kernel/知识。实质修订命题时保留原文、原因、旧命题状态及其反例，分别报告原假设与修订结论；不能用修订命题得到支持宣称 Chief 给定的原假设成立。看过数据后拟定的范围或幅度先标为探索性解释；同一批数据可支持对这些观测的描述，不能再当作对新预测的独立验证。稳定性和未测范围保留待验证，不能只把测得的数字改写成新命题就宣布原目标完成。最终证据和模块链接采用 prepare 返回的实际产物引用。

## Ascend 性能分析入口

- 首先发现本机 `msprof`、`msprof op` / `msopprof` 的版本与帮助，读取硬件报告列出的能力。CANN 不同版本和芯片支持的指标不同；不照搬最新文档选项到旧环境。
- 普通 `msprof` 的 `op_summary_*.csv` 用于任务类型/名称/设备和时序关联。用于确认执行类型时使用支持该字段的 `--task-time=l1`；l0 可能没有 Task Type。匹配目标 kernel 的 AI_CORE、AI_VECTOR_CORE 或相应 MIX 任务，排除 AI_CPU、搬运与无关 kernel。
- `Task Duration(us)` 包含任务调度、加速器执行和结束响应；`aic_time` 等 PMU 推导值有各自含义，不能互换为 ACL event 时间或总端到端时间。只有实际采集到的字段才能支持相应解释。
- 单算子深入调优可使用 `msprof op` / `msopprof`，按本机能力选择 PipeUtilization、Memory、L2Cache 等，指定目标 kernel。记录 replay/cache 行为和预热；profiling 结果单独分析。同一设备不并发 profiler，调试流程由当前 Agent 按需调用。

命令模板、字段解释、硬件监控与版本明确的官方来源见 [Ascend 测量参考](../meteor-kernel-test/references/ascend-measurement.md)。执行设备证明用于判断实验资格；假设成立与否仍由其预测、对照和实际证据决定。

在原 session 内加载和使用此 skill，保留 memory.md、实验沿革和证据引用。不要创建分析/总结子 Agent，不操作集成 version。
