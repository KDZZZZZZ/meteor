# 性能与机制分析

## Chief：形成假设并衔接下一轮

用户给出目标后，Chief 可读取少量相关内部文件和库证据，使用可用 web 工具检索厂商官方资料，形成有依据的可证伪假设。依据足以安排实验时，按 `meteor-kernel-test` 的 Chief 入口完成初始化、配置与启动；不要穷尽源码或旧日志。可在 `meteor_start` 中用 `hypothesis` 指定本轮要验证的目标，独立搭配随机或指定初始材料；未提供时才由研究 Agent 提出假设。

收齐研究报告和自动集成回执后，分别检查原假设结论、kernel 证据和总目标进展。已有持续授权且首轮稳定时，在总预算、单研究预算和设备能力内自主安排下一轮；用原生 jobs 和可用的持久目标能力管理进度，不将一次研究结束当成总目标完成。远端状态未知的请求先查询或收取，不重复启动。

Chief 可根据报告中的具体行为缺口改善现有项目 persona/两个 skill，并让未来研究使用新快照。保留运行中的快照、原始回执和提交结果，不中途喂提示或手工修补结论。所有凭据继续由集中配置引用。

## 研究 Agent：在原会话内分析

把分析落到可检验的预测和最小对照实验。检索到足够支持实验设计的材料后就开始测量；不要求先穷尽所有可能优化。预算不足时，整理已有证据并明确不确定性，不通过长篇推演替代实验或编造可交付结果。

核对 manifest.json、seed.json 中的 Chief 输入与实际分发。指定 kernel/知识仍只作启发，允许自主检索和选择其他实现。

1. 重读原假设、关键预测、支持/反证标准和所有 revision。Chief 已给定假设时保留其原文，补齐实验定义；避免根据结果事后替换命题。
2. 核对实验干预确实生效；对照具有可比的 case、输入、环境、协议和测量条件。检查错误实现、缓存、并发、编译设置及计时噪声。
3. 按需调用 `meteor_kernel_profile`，选择一个具体 build_ref、case_ids 和 metrics。部分 case 的 profile 可以解释机制，不能取代完整全尺寸测试。
4. 区分插桩 profile 与未插桩计时，不能混用。硬件观测必须关联精确实现和环境；模拟指标不得支持真实硬件命题。
5. 比较原始样本与配对/重复测量，说明观测、解释、支持证据、相反证据和仍未排除的因素。必要时新增消融或返回编码。
6. 分别陈述机制变化与整体 kernel 性能。全尺寸最优不证明机制，全尺寸更差也不自动否定机制；若原假设预测总耗时降低，就必须检验该预测。
7. 当前 Agent 根据实际证据和原标准给出 SUPPORTED/REFUTED/INCONCLUSIVE。宿主不以单一阈值代替科学判断。
8. 在 report 中提出下一步建议及理由，可引用任何兼容 kernel/知识。实质修订命题时保留原文、原因、旧命题状态及其反例，分别报告原假设与修订结论；不能用修订命题得到支持宣称 Chief 给定的原假设成立。

在原 session 内加载和使用此 skill，保留 memory.md、实验沿革和证据引用。不要创建分析/总结子 Agent，不操作集成 version。
